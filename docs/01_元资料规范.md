# 工作台元资料规范 v1.0

> 目的：让所有进展、经验、产出形成**AI可读、可交接、可复用**的元资产；任何AI拿到资料包即可理解上下文并干活。
> 版本：v1.0 ｜ 2026-08-30 ｜ 维护：运营搭子

---

## 一、什么是元资料

元资料 = 描述"工作台怎么运转"的资料，不是业务数据本身。分六类：

| 类型 | 文件名前缀 | 内容 | 例子 |
|---|---|---|---|
| 总纲 | `00_` | 工作台全貌、原则、分工、资产地图 | 00_工作台总纲.md |
| 规范 | `01_` | 写作/留存/命名/流程标准 | 01_元资料规范.md |
| 场景SOP | `SOP_` | 一个场景的完整操作定义：触发条件→输入→处理步骤→输出格式→异常处理→验收标准 | SOP_经营诊断.md（待建） |
| 认知卡片 | `认知卡片NNN_` | 六段结构：出发点/优秀点/衔接性/使用法/升级路/借鉴值 | 认知卡片001_评价采集工作台.md |
| 调研报告 | `*_report` / `调研_` | 外部学习、标杆拆解 | AI工作台案例调研_report.md |
| 决策日志 | `决策日志_` | 关键决策：背景→选项→决定→理由→复盘 | 决策日志_MVP方向.md（待建） |

## 二、文档标准头（每份元资料必须有）

```markdown
> 版本：vX.Y ｜ 更新：YYYY-MM-DD ｜ 状态：草稿/在用/废弃 ｜ 维护：XXX ｜ 依赖：相关文档
```

- 实质性修改升版本号，文末附「变更记录」
- 状态为"废弃"的文件不删除，头部标注废弃原因和替代文档

## 三、留存三级架构

```
第一级：飞书多维表格 = 结构化台账（能力/场景/认知索引/复盘记录）
        → 人高频看、协作、看板；长文正文不放飞书，只放索引+关键字段
第二级：项目目录 /Coze/Drive/Github优质脚本/工作台建设/ = 元资料主阵地
        → AI直接读写；SOP/认知卡片/规范/报告的完整正文
第三级：GitHub ai-ecommerce-digest 仓库 docs/ = 版本化副本
        → 跨设备/跨AI共享、历史版本追溯；hermes负责从项目目录同步
```

**规则**：
- 元资料**先写项目目录（第二级）**，稳定后同步GitHub（第三级）；飞书（第一级）只登记索引行（文档名+一句话摘要+链接+状态）
- 大文件（素材、视频、图片）不进Git，走本地+XBserver
- 数据原材料Excel：上传项目目录 `工作台建设/数据原材料/`，用完归档到 `数据原材料/归档/`

## 四、命名规范

- 文件名只用：中英文、数字、下划线、短横线；**禁止空格和特殊字符**
- 格式：`类型前缀_主题_版本或日期.md`，如 `SOP_经营诊断_v1.md`、`认知卡片002_经营诊断MVP.md`
- 日期格式统一 `YYYY-MM-DD`；编号三位数（001、002…）

## 五、写作原则（给AI看的文档怎么写）

1. **结构化优先**：多用表格、编号列表、固定字段；少用修辞段落
2. **接口严格**：SOP中每个环节的输入/输出必须写明格式（字段名、类型、示例），禁止"AI自行理解"——WorkBuddy小红书案例的教训：节点接口不严谨会导致整条流水线产出废品
3. **数字必有据**：所有效率数字、功能描述标注来源；查不到来源不写
4. **可执行**：SOP要写到"另一个AI照着做能复现"的程度
5. **单一事实源**：同一信息只在一个文档定义，其他文档引用而非复制（复制了就要同步维护，避免不一致）

## 六、更新机制

- 每次场景跑通/修改 → 当天更新对应SOP
- 每周复盘 → 产出1张认知卡片或更新策略库
- 总纲每月或重大架构调整时更新版本
- 运营搭子负责元资料质量审核；hermes同步GitHub；红光随时可抽查

## 七、给其他AI的交接话术（红光可直接复制）

当需要让 WorkBuddy / Codex / 新AI承接任务时，红光只需说：

> "先读项目目录 `/Coze/Drive/Github优质脚本/工作台建设/` 下的 `00_工作台总纲.md` 和 `01_元资料规范.md`，按总纲§6的交接包顺序读完后，再处理以下任务：[具体任务]"
